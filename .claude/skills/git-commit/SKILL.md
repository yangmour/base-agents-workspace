# Git 提交技能

使用此技能在当前多仓库工作区中准备并创建高质量 Git 提交。

当前工作区是多仓库目录，顶层目录不是 Git 仓库。提交前先确认变更属于哪个子仓库，再在对应仓库内执行 Git 命令。

## 核心原则

一个好的提交应当具备以下特征：

- **原子性**：一次提交只包含一个逻辑变更。
- **完整性**：除非用户明确要求提交半成品，否则相关代码应能通过对应范围的构建或测试。
- **可读性**：提交信息说明变更意图和影响，而不是逐项复述文件改动。
- **可追踪性**：相关文件一起提交，无关变更留在工作区。
- **安全性**：不要提交密钥、生成垃圾、依赖缓存或误加入的本地文件。

优先创建少量清晰、内聚的提交，而不是把无关修复、格式化、生成文件和功能开发混在一个提交里。

## 必须遵循的流程

当用户要求提交代码时，按以下流程执行。

### 1. 确认仓库和当前状态

从包含变更的子仓库执行 Git 命令，不要在工作区根目录执行。

检查：

```bash
git status --short
git diff --stat
git diff
git diff --cached
git log --oneline -5
```

如果多个子仓库都有变更，先汇报各仓库状态，并询问用户要先提交哪个仓库或哪组变更。

### 2. 判断变更粒度

判断当前变更是否属于一个逻辑单元，还是应该拆成多个提交。

以下情况通常应拆分提交：

- 功能实现和无关格式化混在一起
- 后端 API 变更和可独立提交的前端 UI 变更混在一起
- 依赖升级和业务逻辑变更混在一起
- 重构和行为变更混在一起
- 生成文件和源码修改混在一起

如果用户要求一个提交，但 diff 明显包含多个无关主题，先说明建议的拆分方式，再进行暂存。

### 3. 暂存前检查风险

不要在未检查 diff 的情况下直接使用 `git add .` 或 `git add -A`。除非用户明确要求，并且你已经检查过变更内容。

重点排查通常不应提交的文件：

- `.env`、`.env.*`、凭证、令牌、私钥、证书
- 项目未跟踪的 IDE 元数据
- 日志、转储文件、临时文件、构建产物、缓存目录
- 非项目预期的大型二进制文件或生成产物
- 其他任务遗留的无关本地修改

只暂存属于当前提交主题的具体文件或 hunk。

### 4. 尽量执行验证

提交实现类变更前，运行与本次修改范围最匹配、最窄的验证命令。

当前工作区常用示例：

```bash
# java-base-module
mvn -pl <module> -am test -Drevision=1.0

# node-base-module/base-admin-web
npm run type-check
npm run build

# node-base-module/deploy-transform
npm test
npm run build
```

如果因为耗时过长、环境缺失，或用户要求立即提交而跳过验证，需要在最终回复中说明。

不要用 `--no-verify` 绕过失败的 hook 或测试。应先修复问题，或询问用户如何处理。

### 5. 编写提交信息

除非仓库历史明显采用其他风格，否则使用 Conventional Commits。

提交信息的标题和正文都使用中文表达；`type` 和可选 `scope` 保持 Conventional Commits 的英文标识，例如 `fix(jenkins): 修复 AI 工具静态资源打包`。

不要在提交信息中添加 `Co-Authored-By` 等协作者标签，除非用户当次明确要求。

格式：

```text
<type>(<scope>): <summary>

<body，可选>
```

常用类型：

- `feat`：新增用户可感知的功能或能力
- `fix`：修复缺陷
- `refactor`：不改变行为的代码结构调整
- `perf`：性能优化
- `test`：仅测试相关变更
- `docs`：仅文档变更
- `style`：仅格式化变更，不改变行为
- `build`：构建系统、依赖、打包相关变更
- `ci`：CI/CD 配置变更
- `chore`：其他维护性变更

摘要规则：

- 使用中文祈使句或动宾短语描述变更，例如 `修复静态资源打包`、`更新部署配置`。
- 保持简洁，建议不超过 72 个字符。
- 末尾不要加句号。
- 有助于理解时添加 scope，例如 `fix(auth): 修复刷新令牌过期校验`、`feat(admin): 增加角色权限编辑器`。

正文规则：

- 当变更原因、迁移影响或行为变化不明显时，添加正文。
- 正文解释为什么要改，以及有什么重要影响。
- 不要重复文件列表。

### 6. 安全创建提交

创建新的提交。除非用户明确要求 amend，否则不要修改已有提交。

使用 heredoc 传递提交信息：

```bash
git commit -m "$(cat <<'EOF'
<type>(<scope>): <summary>

<body，如需要>
EOF
)"
```

提交后运行：

```bash
git status --short
```

最后汇报提交哈希和剩余未提交文件。

## 提交信息示例

```text
feat(admin): 增加角色权限编辑器
```

```text
fix(auth): 拒绝已过期的刷新令牌

刷新令牌过期后仍会被刷新流程接受，可能导致无效会话存活时间超过预期。
```

```text
refactor(redis): 简化缓存键生成逻辑
```

```text
test(deploy-transform): 补充 ingress 转换告警用例
```

## 只要求编写提交信息时

如果用户只是要求写提交信息，没有要求实际创建提交：

1. 如果可以读取 diff，先检查 diff。
2. 给出一个推荐提交信息。
3. 如果变更混杂，按逻辑变更分组给出多个提交信息。
4. 不要暂存或提交任何文件。

## 最终回复格式

创建提交后，简短回复：

```text
已创建提交 `<short-hash>`：`<subject>`。
验证：<命令和结果，或跳过原因>。
剩余未提交变更：<无，或简要说明>。
```
