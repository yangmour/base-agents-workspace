# 上传完成未知结果的关闭与持久恢复

## 范围与选择

延续 G2 既有不可变发布设计中“HEAD 恢复或撤销发布资格并保留墓碑”的选择，补齐签发 ledger 的 `FINALIZING` 退出路径。本切片保持后台界面、认证、OMIT 幂等以及 S3 complete 单 attempt；不重放 complete，不以 HEAD 404 或网络超时推断远端写入已经停止。

新 admin 签发已拥有唯一文件、不可变物理地址快照和永久 artifact。原身份 CANCEL 或原签发期限到期可以关闭这类资源：数据库事务先锁定当前 file，验证同租户 ledger/artifact，再撤销发布资格、留下 TOMBSTONE 并释放一次预留。存储 abort/delete 只在提交后尽力执行。远端迟到对象仍被原墓碑反复扫描；配额统计已发布文件与有效预留，不代表临时存储的物理硬上限。

普通 multipart 的 `COMPLETING` 使用同一规则。完成结算先锁当前 file，再检查原完成身份及状态；若关闭胜出，迟到完成不能提交 quota 或保护 artifact。完成先胜出则 CANCEL 返回 COMPLETED，不能删除已发布文件。统一 file → artifact → quota 的事务顺序，避免旧完成流程 quota → file 与取消相反。保留旧无 ledger 记录的 HEAD 恢复兼容路径；缺少地址证据时不新增自动终止，不按当前 prefix 猜测历史地址。

## 恢复调度

普通 multipart 三种恢复队列（COMPLETING、ABORTING、REJECTING_OVERSIZE）按固定本轮上界和 id keyset 遍历，单条缺对象或错误不能饿死后续行。确切 S3 对象不存在为 pending；权限、网络、DB 和快照损坏按安全类型与数量聚合，继续处理后使 XXL 任务失败。不存在对象不授权重新 complete。

`fileMultipartRecovery` 保留无参数全局运维兼容，并支持严格精确 tenantId/moduleCode 参数用于受控恢复；非法或半个 scope 必须失败，不得退回全局。精确恢复可对该 scope 的到期 ledger 执行上述原子关闭，并处理墓碑。全局到期任务同样纳入正在完成的有快照 ledger。

墓碑清理依旧保存当前不存在的观察和下一次检查时间，永不把一次 404 当成永久清理证明。单条存储错误必须持久记录并在批末汇总失败；已提交的用户取消可以通过现有 best-effort 包装返回逻辑终态，不能冒称物理对象已永久消失。

先记录当前实现的 RED：FINALIZING CANCEL 无效、到期扫描排除、关闭后迟到结算顺序、首 100 条缺对象阻塞第 101 条、403 被任务报成功。补真实 MySQL 双上下文竞争与事务回滚；固定独立源码快照构建。

真实验收使用新夹具、独立桶、独立 file JVM 和只作用于该 JVM 的 loopback S3 代理。覆盖领取后尚未转发请求即强杀、远端已提交但回执丢失、关闭后的迟到完成、第二实例 HEAD 恢复、过期关闭和重复墓碑扫描。代理必须真实转发 S3，不伪造成功响应；原始签名、uploadId、密码和令牌仅留私有内存或忽略文件。仅停止本轮拥有的进程，不修改共享 MinIO。
