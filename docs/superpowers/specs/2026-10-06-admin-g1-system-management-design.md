## 背景与目标

`java-base-module/server/admin` 与 `node-base-module/base-admin-web` 已经具备后台独立认证、用户/组织/角色/数据范围、菜单目录、租户套餐、审计和在线用户的基础实现。现有文档和测试证明了 G0、组织/岗位以及角色/数据范围的阶段性结果，但还不能证明菜单/按钮、套餐候选、租户与审计/在线用户已经形成可重复的真实闭环。

本阶段目标是沿用现有前端风格和 `RI<T>` 契约，把剩余系统管理能力按三个可独立提交的垂直切片补齐，并用真实 admin、数据库、Redis 和浏览器验证：

1. 菜单/按钮目录读写、动态路由和按钮权限收敛。
2. 套餐/租户授权候选与跨租户数据隔离。
3. 登录日志、操作日志和在线会话强退。

每个切片都必须有后端约束、前端可见行为、真实 HTTP/浏览器用例、中文注释和独立提交。文件、代码生成、XXL-Job、监控、客户端 SSO 以及业务域扩展不属于本阶段。

## 现状约束

- 后台账号、凭证、JWT、刷新、会话和 RBAC 由 `admin` 独立负责；`auth-center` 不作为本阶段登录依赖。
- 菜单目录是平台共享数据，租户只持有套餐菜单引用；菜单写入已经使用目录锁、父链校验、乐观版本和幂等键。
- 前端动态组件只能来自显式注册表，后端不得把任意文件路径下发给浏览器。
- Long 标识必须使用 `Identifier`/字符串键保留完整精度；前端不能依据 JavaScript 安全整数进行截断。
- 服务端始终负责最终授权。页面隐藏按钮和移除动态路由只是用户体验，不能替代接口权限检查。
- 测试凭据只从环境读取；测试报告、截图和日志不得保存密码、Token、请求头或完整敏感载荷。

## 方案与取舍

采用垂直切片，而不是先做一次性后端重写或先搭建双 Pod 测试平台。每个切片都同时修改后端、前端和验收套件，因此可以在真实页面上尽早发现契约问题；跨切片共用现有的权限快照、租户上下文、幂等写入和审计机制，避免复制第二套安全模型。

三个切片按依赖顺序执行：菜单/按钮提供权限目录，套餐/租户决定可授权候选，审计/在线用户记录并控制前两个切片产生的会话与操作。每个切片完成后先验证再提交，下一切片只依赖已提交的接口和页面契约。

## 设计

### 1. 菜单/按钮目录与权限收敛

后端继续使用 `MenuApplicationService` 及现有 `MenuManagementController`。目录写事务统一取得数据库目录锁，再执行父链、子类型、重复编码、组件注册表和版本校验。目录节点分为目录、页面和按钮：目录可以承载目录或页面，页面可以承载按钮，按钮不能有子节点；页面组件只能取显式注册表中的键。删除前检查子节点、套餐引用和角色引用；冲突返回 409，前端关闭旧表单并提示重新加载。

前端 `system/menu` 页面继续使用当前表格、弹窗和权限指令。真实用例覆盖新增、编辑、删除保护、重复路由/权限编码、非法父子组合、版本冲突和停用后的路由/按钮变化。权限版本变更后由现有轮询和路由切换检查加载最新快照；不通过焦点、可见性或整页刷新制造额外同步。

### 2. 套餐/租户授权候选与隔离

套餐菜单候选从当前有效平台目录计算，停用、删除或不在套餐范围内的节点不能被新增授权。保存授权使用现有 200 项上限、版本冲突和幂等边界；事务内校验整棵选择集合，不能静默截断或把隐藏祖先变成可绕过的授权。

真实验收使用两个独立租户、管理员和受限用户：管理员可以维护套餐/租户及授权，受限用户只能读取其租户套餐允许的页面和按钮；直接调用其他租户 ID、伪造租户头、已停用菜单或越权写接口都必须被拒绝。租户启停、套餐变更和权限撤销后，已有 Token 不自动失效，但服务端在下一次授权判断时必须拒绝失去的操作，前端在可见页面的现有收敛周期内移除入口。

### 3. 审计日志与在线用户

登录日志和操作日志继续由 admin 本地服务写入并分页读取，查询支持现有的用户、模块、类型和时间范围筛选。响应只提供脱敏摘要，禁止暴露密码、Token、内部签名或完整请求正文；开始时间晚于结束时间时返回明确的业务错误。前端查询失败时保留已经展示的数据，提供重试，不把网络错误当作空列表。

在线用户页面继续分页展示客户端、设备、IP、最后活跃和会话过期时间，使用字符串化 `sessionId` 维护 pending 集合。强退必须经过权限检查、幂等键和确认弹窗；成功后刷新列表，旧 access/refresh Token 在另一实例请求受保护接口时立即被拒绝。强退自身会话的业务规则按服务端现有实现验证并记录，不由前端猜测。

## 数据流与并发边界

浏览器只访问 `/admin-api`。请求拦截器携带后台 Token、请求 ID 和租户上下文，由 admin 从已验证会话取得可信用户/租户，不接受浏览器传入的租户标识作为授权依据。读请求可在一次共享刷新中恢复；写请求失败不自动重放，所有创建、更新、删除、授权和强退请求显式携带幂等键。

菜单目录写入在数据库目录锁内完成父链与引用检查；套餐/租户写入使用行锁或乐观版本；权限版本通过 Redis 共享失效，确保多 Pod 不依赖本地内存。在线会话强退写入共享会话撤销状态，另一 Pod 的鉴权链在下一请求读取同一撤销结果。日志写入失败不得改变主业务提交结果，但必须产生可观测的失败记录或指标。

## 错误处理

- 401：清理本地后台会话并跳转登录；只在允许的 GET 场景进行一次共享刷新。
- 403：保留当前身份状态，显示正式无权限页或错误提示；不能回退到客户端 SSO。
- 409：关闭陈旧表单/授权弹窗，提示重新加载当前数据。
- 业务校验错误：在表单或页面内展示可理解的中文错误，不吞掉服务端错误码。
- 网络/依赖错误：保留已有数据，显示重试入口；轮询请求失败不撤销现有权限快照。

## 测试与验收

每个切片按以下层次验证：

1. Java 单元/集成测试：父子菜单与版本冲突、套餐候选与上限、租户隔离、日志筛选/脱敏、会话强退和共享缓存失效。
2. 前端组件/契约测试：表单校验、按钮可见性、Long 标识、409/403/网络错误和失败后数据保留。
3. 真实 HTTP 套件：两个租户、管理员与受限用户、匿名/伪造租户头/越权写入、权限撤销、强退和幂等重试。
4. Playwright 冒烟：真实登录后依次操作菜单/套餐/租户/日志/在线用户，至少连续运行两轮；记录页面异常数、HTTP/RI 状态、权限收敛时间、清理状态和截图路径。
5. 双 Pod 验证：A 实例执行菜单/授权/强退，B 实例读取动态权限或访问受保护接口；共享 MySQL/Redis 下结果必须一致。Pod 重启或短暂依赖不可用时，不得恢复已撤销权限，也不得重复写入。

退出条件是三个切片的真实浏览器与 HTTP 套件均通过，越权矩阵和清理均无失败，前端 `npm test`、`npm run type-check`、`npm run build` 通过，Java 对应模块测试通过，运行手册和进度表记录实际命令与结果。历史截图、Mock 响应或编译成功不能单独作为通过证据。

## 风险与边界

- 当前工作区存在其他未提交文档和前端边界测试改动；实现时必须先区分本阶段文件，避免把无关改动带入提交。
- 本阶段只证明系统管理在现有 admin 认证域中的真实闭环，不证明 auth-center SSO、文件对象存储、调度中心、监控数据源或业务域完成。
- 权限轮询已有约 15–18 秒的实测收敛周期；验收应记录实测上界，不能把固定等待写成永久保证。
- 多 Pod 测试需要真实共享数据库/Redis 和可识别的实例标识；两个本地进程不自动等价于生产 K8s 验收。
