# 项目全面重构优化设计

> 日期：2026-07-10
>
> 范围：`java-base-module`、`node-base-module/base-admin-web`、`node-base-module/weixin-bot-admin`
>
> 状态：可评审版，已按代码复扫校正

## 1. 背景

本项目已经具备后端多模块、管理后台、文件服务、权限模型和本地开发环境，但代码压力点开始集中出现：

- 后端权限码、菜单模型、请求上下文和前端按钮权限存在口径分叉。
- 文件服务功能完整但类职责偏重，上传、回调、统计、配额、媒体处理、调度、存储 provider 混在较少的核心类中。
- 管理后台已经支撑动态路由和权限展示，但 `router`、`request`、`layout`、用户/角色页面都偏大，且存在 `any`、fallback 路由、状态耦合。
- `weixin-bot-admin` 仍像轻量模板项目，尚未纳入统一后台或统一请求契约。

用户已确认三块代码都可以完全重构。本文档先定义重构方向、边界和分阶段计划，不直接改业务代码。

### 2.2 契约与权限问题

发现的典型分叉：

- 后端管理接口使用 `menu:view`、`course:view`、`class:create` 等权限码。
- 前端按钮使用 `system:menu:create`、`system:user:create`、`system:role:assign` 等权限码。
- `auth-center`、`admin`、`education` 都有菜单/权限相关逻辑，权限命名缺少统一注册表。
- `BusinessLine` 前端是 `COMMON/MALL/EDUCATION`，部分后端服务仍出现 `"DEFAULT"`、硬编码 `"COMMON"`、硬编码 `"WEB"`。
- 前端有 `RouteSnapshot` 类型，但当前 `getCurrentUserMenus()` 仍主要拉 `MenuTreeVO[]`，权限版本和按钮权限没有形成一个稳定快照接口。

复扫得到的权限码实际列表：

| 来源 | 权限码 |
|---|---|
| 后端 `@RequiresPermission` | `menu:view`、`menu:create`、`menu:update`、`menu:delete`、`course:view`、`course:create`、`course:update`、`course:delete`、`class:view`、`class:create`、`class:update`、`class:enroll`、`student:view` |
| 前端 `v-permission` | `system:menu:create`、`system:menu:update`、`system:menu:delete`、`system:user:create`、`system:user:update`、`system:user:reset-password`、`system:user:delete`、`system:role:create`、`system:role:update`、`system:role:assign`、`system:role:delete` |

结论：必须先做权限码注册表和兼容映射。否则直接拆前端或后端接口会放大权限错配。

### 2.3 文件服务问题

文件服务当前功能面较宽：

- 上传凭证、文件信息、批量查询、下载 URL、删除、分片上传。
- 模块配置、配额统计、共享、审计。
- 媒体处理、缩略图、视频封面。
- 清理调度、失败任务重试、迁移。
- S3/MinIO provider，OSS/COS 仍处于待实现标记状态。

问题不是功能缺失，而是边界不够硬。建议按 use case、domain、infrastructure 分层，让每个类只承接一个变化原因。

复扫得到的文件服务 public surface：

| 类 | public 方法 |
|---|---|
| `InnerFileController` | 上传凭证、文件信息、下载 URL、批量下载 URL、删除、批量删除、批量文件信息、分页、统计、业务绑定查询、分片 init/part/complete/abort |
| `FileObjectServiceImpl` | 上传凭证、回调、查询、删除、下载 URL、批量查询、分页、统计、分片 init/part/complete/abort |
| `S3StorageProvider` | provider 生命周期、上传/下载/删除、存在性、metadata、预签名上传/下载、分片上传、bucket 管理 |
| `FileCleanupScheduler` | 临时文件清理、过期文件清理、孤儿文件清理、存储指标更新 |
| `FailedTaskRetryScheduler` | 失败任务重试、成功任务清理、最终失败告警 |

结论：文件服务重构必须先固定 public surface，再按 use case 切分。不能先移动 controller 路径。

- `router/index.ts` 中存在 `record: any`、`meta as any`、`catch (error: any)`。

- `localStorage` 读写分散在 request、auth-token、layout。

复扫得到的前端具体问题：

| 类型 | 位置 |
|---|---|

| localStorage 分散 | `auth-token.ts`、`utils/request.ts`、`layout/index.vue` |
| 调试输出 | `router/index.ts`、`stores/user.ts`、多个页面和 `request.ts` |
| 测试缺口 | `base-admin-web` 当前未发现 `*.test.ts` 或 `*.spec.ts` |

结论：前端重构前应先建立类型和路由构造测试，否则拆分大页面后无法快速判断行为是否保持。

## 3. 重构目标

### 3.1 总目标

把项目从“功能可用的多模块集合”重构为“契约稳定、边界清晰、可分阶段演进的平台底座”。

### 3.2 非目标

- 不一次性重写所有业务服务。
- 不在第一阶段替换 Spring Boot、Vue、Vite、MyBatis-Plus 等技术栈。
- 不把 `weixin-bot-admin` 直接迁移进主后台，除非先完成入口定位决策。
- 不先做 UI 视觉大改。前端重构优先解决状态、路由、类型和模块边界。

## 4. 方案选择

### 方案 A：契约权限优先，再拆服务和前端

先统一权限码、请求上下文、菜单/路由快照、Token 刷新和前后端类型契约。随后以稳定契约拆 `file` 和 `base-admin-web`。

优点：

- 后续所有重构都有稳定接口，不会反复改前端和后端。
- 最先处理安全边界，降低权限错配风险。
- 可用小步提交建立统一测试和验收。

缺点：

- 前期会做较多盘点、映射和兼容层，短期看不到大 UI 或大服务拆分效果。

### 方案 B：文件服务优先

直接从 `server/file` 开始，拆 `FileObjectServiceImpl`、`StorageServiceImpl`、`S3StorageProvider`、调度任务和媒体处理。

优点：

- 命中最近提交热点，最直接降低文件服务维护成本。
- 文件服务边界相对独立，可控性较高。

缺点：

- 权限码、请求上下文、前端契约仍不稳定，后续接入后台管理还会返工。

### 方案 C：前端后台优先

先拆 `base-admin-web` 的路由、请求、布局、用户/角色页面，建立 composables、feature modules 和类型边界。

优点：

- 管理后台开发体验改善快。
- 类型和组件边界变清楚。

缺点：

- 如果后端权限码和菜单快照未统一，前端重构会被后端契约变化牵动。

### 推荐

采用 **A → B → C** 的顺序：

1. 先收敛契约与权限。
2. 再深拆文件服务。
3. 最后重构前端后台，并决定 `weixin-bot-admin` 是并入还是独立。

## 5. 总体设计

### 5.1 契约与权限重构

#### 目标结构

```text
auth-feignClient
├── enums
│   ├── BusinessLine
│   ├── ApplicationCode
│   ├── ClientType
│   └── PermissionCode
├── dto
│   └── UserPermissionDTO
├── vo
│   ├── MenuTreeVO
│   └── RouteSnapshotVO
└── request
    └── PermissionCheckRequest
```

#### 关键决策

1. 新增统一权限码注册表，采用 `domain:resource:action` 或现有 `system:user:create` 风格。推荐收敛到三段式：`system:user:create`、`system:menu:view`、`education:course:view`。
2. 后端 `@RequiresPermission` 和前端 `v-permission` 必须使用同一套权限码。
3. `RouteSnapshotVO` 成为管理端启动快照，包含：
   - `version`
   - `permissionVersion`
   - `menus: MenuTreeVO[]`
   - `buttonPermissions: string[]`
   - `profile: UserPermissionDTO`
4. `MenuTreeVO` 继续作为菜单和动态路由主模型，不新增第二套路由模型。
5. `BusinessLine` 不允许出现 `DEFAULT` 作为长期业务线。需要兼容时只能作为迁移值，并在转换层归一化。

#### 影响文件

- 后端：
  - `common/base-feignClients/auth-feignClient`
  - `common/base-authz`
  - `common/base-security`
  - `server/auth-center`
  - `server/admin`
  - `server/education`
  - `server/im`
- 前端：
  - `base-admin-web/src/types/api.d.ts`
  - `base-admin-web/src/api/auth.ts`
  - `base-admin-web/src/stores/user.ts`
  - `base-admin-web/src/stores/permission.ts`
  - `base-admin-web/src/router/index.ts`
  - `base-admin-web/src/directives/permission.ts`

### 5.2 文件服务重构

#### 目标包结构

```text
server/file/src/main/java/com/xiwen/server/file/
├── application
│   ├── upload
│   │   ├── CreateUploadCredentialUseCase
│   │   ├── CompleteUploadCallbackUseCase
│   │   └── MultipartUploadUseCase
│   ├── query
│   │   ├── FileInfoQueryService
│   │   └── FileStatisticsQueryService
│   ├── lifecycle
│   │   ├── DeleteFileUseCase
│   │   ├── CleanupOrphanFileUseCase
│   │   └── MigrateFileUseCase
│   └── media
│       └── ProcessMediaUseCase
├── domain
│   ├── model
│   ├── policy
│   └── event
├── infrastructure
│   ├── persistence
│   ├── storage
│   ├── scheduler
│   └── media
└── interfaces
    ├── inner
    └── callback
```

#### 拆分原则

| 当前职责 | 新位置 | 说明 |
|---|---|---|
| 申请上传凭证 | `application/upload/CreateUploadCredentialUseCase` | 只编排模块校验、配额、存储签名、文件记录 |
| 上传回调 | `application/upload/CompleteUploadCallbackUseCase` | 只处理状态推进、大小校验、媒体任务、审计 |
| 下载 URL | `application/query/FileInfoQueryService` + `infrastructure/storage` | 查询和签名分离 |
| 分片上传 | `application/upload/MultipartUploadUseCase` | 初始化、part URL、complete、abort 统一 |
| 配额 | `domain/policy/FileQuotaPolicy` | 配额判断不散落在 service 中 |
| 审计 | `domain/event/FileAuditEvent` + audit service | 事件语义固定 |
| 媒体处理 | `application/media` + `infrastructure/media` | use case 与 Thumbnail/Video 具体实现分离 |
| 调度任务 | `infrastructure/scheduler` | 调度只触发 use case，不写业务细节 |
| S3 provider | `infrastructure/storage/s3` | provider 只处理 SDK，不处理业务状态 |

#### 迁移策略

1. 先补 characterization tests，固定现有行为。
2. 保留原 `FileObjectService` 接口作为 facade，内部逐步转发到 use case。
3. 每次只迁移一组路径：上传凭证 → 回调 → 查询/下载 → 分片 → 清理/迁移。
4. 最后收缩旧实现类，删除重复逻辑。

## 6. 数据流设计

### 6.1 登录和权限启动流

```text
login request
  -> auth-center login
  -> accessToken + refreshToken + user
  -> route snapshot
      -> menus
      -> buttonPermissions
      -> permissionVersion
      -> profile
  -> frontend registers dynamic routes
  -> frontend stores permission profile
```

### 6.2 后台 API 权限流

```text
request
  -> api-gateway injects trace / cleans trusted headers
  -> service JwtAuthenticationFilter validates token
  -> PermissionAuthorizationManager reads @RequiresPermission
  -> SecurityAuthProvider loads PermissionProfile
  -> RBAC check
  -> optional ABAC check
  -> controller use case
```

### 6.3 文件上传流

```text
client asks credential
  -> CreateUploadCredentialUseCase
      -> module policy
      -> quota policy
      -> storage provider presign
      -> file object draft
  -> client direct uploads
  -> callback
      -> CompleteUploadCallbackUseCase
      -> verify object metadata
      -> update status
      -> emit media/audit tasks
```

## 7. 错误处理

### 后端

- Controller 返回 `RI<T>`。
- Feign Client 返回业务 DTO/VO，由 `FeignUnwrapConfiguration` 解包。
- 业务错误抛 `BizException` 或返回统一业务错误码。
- 权限错误区分 401、403 和业务拒绝。
- 文件服务异步失败进入失败任务表，调度任务只重试可重试状态。

### 前端

- HTTP 层统一处理 `code !== 200`。
- 401 刷新 token 只允许单飞。
- 刷新失败必须清理 token、用户信息、动态路由、权限快照。
- 页面层不直接处理底层 axios 错误，只处理业务语义。

## 9. 分阶段计划

### P0：冻结契约和安全边界

1. 输出权限码注册表。
2. 对齐后端 `@RequiresPermission` 与前端 `v-permission`。建议目标权限码：
   - 系统域：`system:menu:view/create/update/delete`、`system:user:view/create/update/delete/reset-password`、`system:role:view/create/update/delete/assign`
   - 教育域：`education:course:view/create/update/delete`、`education:class:view/create/update`、`education:student:view`、`education:enrollment:create`
3. 增加 `RouteSnapshotVO` 或明确当前 `MenuTreeVO[]` 到快照的过渡层。
4. 移除长期业务线中的 `"DEFAULT"` 口径。
5. 收紧 `securityMatcher("/**")` 到服务自己的 API 边界。

验收：

- 权限码前后端一致。
- 前端动态路由和按钮权限来自同一快照或兼容层。
- 后端未授权后台 API 默认拒绝。

### P1：文件服务深拆

1. 补行为锁定测试。
2. 先只在 `FileObjectServiceImpl` 内部引入 use case，不改 controller 和 Feign 契约。
3. 拆上传凭证 use case。
4. 拆回调 use case。
5. 拆查询和下载 URL。
6. 拆分片上传。
7. 拆清理、失败重试、迁移任务。
8. 把 `S3StorageProvider` 拆成 presign、object、multipart、bucket 四类协作者。
9. 清理旧 facade。

验收：

- `FileObjectServiceImpl` 显著瘦身，核心逻辑进入 use case。
- provider 不包含业务状态推进。
- 调度类只触发 use case。

### P2：前端后台结构重构

1. 先补 route builder、permission filter、refresh manager 的测试。
2. 拆 router。
3. 拆 request。
