# 管理平台全量复刻与分布式重构设计

## 1. 目标

在现有多服务工作区内，参考 `ruoyi-vue-pro` 的业务能力和
`yudao-ui-admin-vue3` 的交互模式，重新实现一套可用于生产环境的管理平台。
现有接口、表结构和页面不要求兼容；已有实现只有在边界清晰、测试充分且适合多
Pod 运行时才复用。

最终范围必须包括：

- 用户、部门、岗位、角色、菜单和按钮权限；
- 数据权限、SaaS 多租户、OAuth 2.1/OIDC SSO；
- 登录日志、操作日志和在线用户；
- 代码生成、文件服务、XXL-Job 定时任务、MQ 消息调度中心和监控；
- 工作流、CRM、ERP、商城、支付、AI 和 IoT；
- Vue 3 管理端以及所有上述功能的前后端联调；
- 多 Pod、高并发、故障恢复和水平扩容验证；
- 每个可独立验证的功能形成单独的原子提交。

本设计不直接复制上游源码。上游项目只作为功能、交互和数据模型参考，代码继续
使用 `com.xiwen` 包名、`RI<T>` 响应结构以及本仓库的公共能力。

## 2. 已批准的总体架构

```text
Vue 3 管理端
      |
 API Gateway
      |
 +----+-------------------+
 |                        |
admin                  auth-center
管理域                  OAuth2/OIDC/SSO
租户/组织/RBAC           JWT/凭据/会话/在线用户
数据权限/管理日志         OAuth 客户端与授权同意
 |
 +-- file service
 +-- XXL-Job
 +-- MQ message scheduling center
 +-- Prometheus / Actuator
 +-- BPM / CRM / ERP / Mall / Pay / AI / IoT 服务
```

### 2.1 服务职责

`server/admin` 持有管理域数据和外部管理 API，包括租户、租户套餐、部门、岗位、
管理用户资料、角色、菜单、数据权限以及管理日志查询。它不保存密码、不签发令牌，
也不直接写入其他领域服务的数据表。

`server/auth-center` 持有身份账号、密码摘要、OAuth 客户端、授权码、访问令牌、刷新
令牌、登录日志和在线会话。现有 RSA JWT、Redis 撤销状态、登录限流和网关校验能力
在通过新契约测试后复用并重构为 OAuth 2.1/OIDC 流程。

`server/file` 继续作为独立文件服务。当前尚未提交的文件服务改动属于用户工作，
任何本项目提交都不得夹带这些文件。管理端通过稳定的文件服务 API 管理文件配置、
上传、下载、迁移、配额和生命周期。

XXL-Job 是唯一的业务定时任务调度入口。业务服务只实现幂等 Handler；调度、路由、
分片、失败重试和告警由 XXL-Job 管理。禁止新增依赖单 Pod 的 `@Scheduled` 业务任务。

BPM、CRM、ERP、商城、支付、AI 和 IoT 分别作为独立领域服务或独立 Maven 模块，
通过 API 和领域事件协作，不把业务实现堆入 `admin`。

### 2.2 外部和内部流量

- 浏览器只访问 API Gateway，不直连内部服务。
- 网关验证外部令牌并保留现有服务入口安全边界。
- 服务间 Feign 请求使用现有 HMAC 签名、时间戳和 nonce 防重放机制。
- 用户、租户、客户端和追踪信息通过受信任的安全上下文传递；普通请求头不能覆盖。
- 跨服务写入通过“本地事务 + 事务后事件 + RabbitMQ inbox/outbox 补偿”完成，不引入
  XA 或全局分布式锁。

## 3. 领域模型

### 3.1 管理域

| 聚合 | 核心数据 | 关键约束 |
| --- | --- | --- |
| 租户 | `tenant`、`tenant_package` | 租户套餐控制菜单和功能；停用租户立即拒绝新会话 |
| 组织 | `department` | 邻接表加物化路径；同租户内编码唯一；移动部门原子更新路径 |
| 岗位 | `post`、`user_post` | 同租户内编码唯一；关联表使用联合唯一索引 |
| 用户资料 | `admin_user` | 不保存密码；通过稳定 `identity_account_id` 关联认证账号 |
| 权限 | `role`、`user_role`、`menu`、`role_menu` | 菜单同时表达目录、页面和按钮权限；权限码全局稳定 |
| 数据范围 | `role_data_scope`、`role_data_scope_dept` | 支持全部、自定义部门、本部门、本部门及下级、仅本人 |
| 审计 | `operation_log` | 追加写；敏感字段脱敏；异步批量落库但不能静默丢失 |

所有可变核心记录包含创建人、创建时间、修改人、修改时间、逻辑删除标记和乐观锁版本。
主键使用现有分布式 ID 能力；关系表建立联合唯一索引，依靠数据库约束消除多 Pod 重复
写入，而不是只依赖 Redis 锁。

### 3.2 认证域

| 聚合 | 核心数据 | 关键约束 |
| --- | --- | --- |
| 身份 | `identity_account`、`identity_binding` | 用户名、手机号、邮箱和第三方身份可绑定同一管理用户 |
| OAuth 客户端 | `oauth_client` | 重定向 URI 精确匹配；密钥只保存强哈希；支持密钥轮换 |
| 授权 | `oauth_consent`、`oauth_authorization_code` | 授权码一次使用；启用 PKCE S256；短有效期 |
| 会话 | `user_session` | Redis 为在线状态热数据，数据库保存可审计会话摘要 |
| 令牌 | `access_token`、`refresh_token` | RSA 签名；刷新令牌轮换；重用检测触发会话族撤销 |
| 登录审计 | `login_log` | 记录租户、账号、客户端、设备、IP、结果和失败原因 |

SSO 基于 OAuth 2.1 Authorization Code + PKCE，并提供 OIDC discovery、JWKS、userinfo、
logout 和 token introspection/revocation。管理端自身也是一个 OAuth 客户端，不使用专有
登录旁路。

### 3.3 租户与数据权限

- 所有租户业务表强制包含 `tenant_id`；平台共享表必须显式进入白名单。
- `tenant_id` 只能来自验证后的令牌和安全上下文，不能由业务请求参数决定。
- MyBatis-Plus 租户拦截器首先追加租户条件，数据权限拦截器随后追加部门或本人条件。
- 自定义 SQL、联表、子查询、批量修改和导出必须有覆盖租户及数据范围的集成测试。
- 超级管理员能力使用显式平台角色和审计事件，不以 `tenant_id = 0` 隐式绕过。
- Feign、RabbitMQ、XXL-Job 和异步线程显式携带可信租户上下文；上下文缺失时默认拒绝。
- Redis key、分布式锁 key、幂等 key 和缓存指标均包含租户维度，但租户输入不得成为
  无界监控标签。

## 4. 后端组件设计

### 4.1 `server/admin` 内部结构

代码按业务能力而不是传统的大型 controller/service/mapper 目录堆叠：

```text
com.xiwen.server.admin
  tenant/
  organization/
  user/
  permission/
  audit/
  integration/
  shared/
```

每个能力目录包含自己的 API、应用服务、领域对象和持久化适配器。Controller 只做协议
转换、Bean Validation 和权限声明；事务、幂等、领域校验与事件发布位于应用服务。

### 4.2 权限决策

菜单决定前端可见路由，按钮权限码决定前端交互可见性，但后端始终独立执行权限校验。
权限快照包含用户、租户、角色、权限码、部门和权限版本。快照缓存在 Redis；Pod 可保留
短 TTL 的本地只读缓存。用户、角色、菜单或组织变更后：

1. 数据库事务递增受影响用户或租户的权限版本；
2. 事务提交后发送失效事件；
3. 所有 Pod 删除本地缓存；
4. 下一次请求比较令牌/快照版本并重新加载权限；
5. 高风险权限回收可同时撤销会话，保证立即生效。

### 4.3 管理 API

外部 API 使用 `/admin-api` 前缀，按资源提供分页、详情、创建、修改、状态变更、删除、
导入和导出操作。统一约束如下：

- 响应继续使用 `RI<T>`，分页响应使用一个统一的 `PageResult<T>`；
- 列表查询限制最大页大小，批量操作限制最大元素数；
- 创建、分配、状态切换等写操作支持幂等键；
- 更新使用版本号或 `If-Match` 防止丢失更新；
- 导入、导出和大批量任务异步执行并提供任务状态，避免占用 Web 线程；
- OpenAPI 文档由服务生成，但生产环境只在受保护的管理网络开放。

### 4.4 代码生成

代码生成位于基础设施能力中，只读取显式配置的数据源和表元数据。模板生成 Java、
TypeScript、Vue 和 SQL 文件，输出到隔离的临时目录或文件服务，绝不在运行中覆盖当前
源码。模板表达式运行在限制上下文中，禁止任意类访问、反射和命令执行。生成物必须先
预览、下载，再由开发者合并。

### 4.5 文件管理

复用独立 `file` 服务的对象存储、分片上传、配额、迁移、过期上传清理和失败任务恢复。
管理平台只新增经过授权的配置与查询入口。上传策略限制扩展名、MIME、大小、租户配额
和对象 key；下载使用短期签名 URL。文件清理和迁移 Handler 必须可重复执行并由
XXL-Job 分片调度。

### 4.6 定时任务

管理端提供 XXL-Job 执行器、Handler、执行记录和失败告警的只读聚合视图；任务创建和
调度配置仍由 XXL-Job Admin 负责，避免复制调度核心。每个 Handler 使用业务幂等键、
分片参数、超时和可恢复检查点。任务不得依赖某个 Pod 的本地磁盘或内存状态。

### 4.7 MQ 消息调度中心

基础设施管理中新增统一的 MQ 消息调度中心。它复用 `base-rabbitmq` 已有的事务
Outbox、消费 Inbox、发布确认、重试拓扑、延迟消息、死信管理和补偿扫描能力，不重新
实现消息代理或第二套任务调度器。

管理入口提供：

- 发送、消费、积压、失败、延迟和死信消息的分页查询与趋势统计；
- 按租户、业务类型、消息 ID、业务 ID、trace ID、交换机和路由键检索；
- Outbox 发布状态、Inbox 消费状态、重试次数、下次重试时间和最终失败原因追踪；
- 单条重试、受限批量重试、死信重放、延迟消息取消以及失败消息导出；
- 基于预注册消息类型创建受控的即时、定时或延迟业务消息；
- 补偿扫描、Outbox 派发和批量重放任务的 XXL-Job Handler 状态与执行记录；
- 重试、取消、重放和人工发送操作的权限审批与完整审计。

消息类型由各领域服务通过代码注册，注册信息包含稳定类型编码、目标 exchange、routing
key、JSON Schema、允许调度的租户范围、最大延迟、最大批量和负责服务。管理端不能任意
填写 exchange、routing key、Java 类型或无约束原始 payload。提交前必须执行 schema、
权限、租户、大小和敏感字段校验，消息内容按安全策略脱敏展示。

业务定时消息由调度中心保存不可变调度记录和幂等键，XXL-Job 分片领取到期记录，再调用
现有可靠发送服务写入 Outbox。多 Pod 依靠数据库原子领取和租约恢复，不依赖本地内存、
本地磁盘或 `@Scheduled`。人工重放生成新的投递尝试并关联原消息，不能覆盖原始审计记录；
消费者继续通过 Inbox 唯一约束保证最终业务结果只执行一次。

批量操作强制设置最大条数、速率上限和并发上限，并支持暂停与熔断。当 RabbitMQ、数据库
或目标服务异常时，任务保留检查点并由 XXL-Job 重试，不能在 Web 请求线程中循环重放。

### 4.8 监控

- Actuator 分离管理端口，只开放 `health`、`info` 和 `prometheus`；
- liveness 不访问外部依赖，readiness 检查必要数据库、Redis 和配置状态；
- Micrometer 指标覆盖 HTTP、数据库连接池、Redis、Feign、RabbitMQ、XXL-Job 和领域
  操作；禁止用户 ID、文件名、租户名称等高基数标签；
- OpenTelemetry trace ID 写入结构化日志和错误响应；
- 审计日志与技术日志分离，敏感字段统一脱敏；
- 运行手册定义多 Pod 滚动发布、优雅停机、缓存失效和任务故障恢复流程。

## 5. 前端设计

`node-base-module/weixin-bot-admin` 完全重构为 TypeScript 项目，使用项目实际锁定版本的
Vue 3、Vite、Element Plus、Vue Router、Pinia、Axios、Vitest 和 Vue Test Utils。

```text
src/
  api/
  components/
  directives/permission/
  layouts/
  router/
  stores/
  types/
  utils/
  views/system/
  views/infra/
  views/infra/mq/
  views/bpm/
  views/crm/
  views/erp/
  views/mall/
  views/pay/
  views/ai/
  views/iot/
```

登录使用 Authorization Code + PKCE 跳转，不把长期令牌放入 `localStorage`。回调完成后
加载用户资料、权限码和后端菜单树，校验组件白名单后生成动态路由。按钮权限由统一
`v-permission` 指令处理，但 API 失败时仍以服务端 `403` 为最终结果。

页面复刻上游的筛选、表格、分页、树选择、抽屉/对话框表单和批量操作体验，但拆成可
测试的小组件。所有请求有取消、超时、统一错误映射和重复提交保护；大列表使用服务端
分页，必要时使用虚拟滚动。生产构建执行按路由拆包、压缩和静态资源长期缓存。

## 6. 错误、安全与并发处理

错误响应包含稳定错误码、用户可读消息、trace ID 和可选字段错误，不返回堆栈、SQL、
内部地址或密钥。鉴权失败使用 `401`，权限不足使用 `403`，资源冲突使用 `409`，乐观锁
冲突使用明确的版本冲突错误。

所有外部输入执行长度、格式、枚举、集合大小和文件限制。富文本使用白名单清洗；查询
只使用绑定参数；重定向地址精确匹配；导出防止公式注入；日志防止换行伪造。平台默认
拒绝跨租户读取、匿名管理接口和未经签名的内部请求。

高并发写入优先依靠数据库唯一约束、乐观锁和幂等表。Redis 锁只用于确实跨记录、跨
资源且无法以数据库约束表达的临界区，并设置租约、等待上限和所有者校验。连接池、Web
线程、异步线程和 Feign 并发数必须有界，所有下游调用设置连接/读取超时和熔断降级。

## 7. 子项目与交付顺序

该目标由以下可独立验收、依次集成的子项目组成，每个子项目拥有自己的详细规格和实施
计划，不以占位页面或空接口视为完成：

1. **平台基础与系统管理域**：租户、套餐、部门、岗位、用户资料、角色、菜单、按钮、
   数据权限、管理端基础框架和首个前后端纵向切片。
2. **认证与 SSO**：OAuth 2.1/OIDC、PKCE、客户端管理、令牌轮换与撤销、登录日志和
   在线用户。
3. **基础设施管理**：操作日志、代码生成、文件管理、XXL-Job 聚合、MQ 消息调度中心和
   监控页面。
4. **工作流**：流程模型、表单、部署、实例、任务、会签/或签、转办、委派、加减签、
   抄送、超时与审计。
5. **CRM**：线索、客户、联系人、商机、合同、回款、跟进和数据权限。
6. **ERP**：商品、采购、销售、库存、盘点、调拨和财务关联。
7. **商城与支付**：商品、订单、营销、售后、支付、退款、回调验签和对账。
8. **AI**：模型配置、知识库、文档处理、对话、工作流以及成本和权限控制。
9. **IoT**：产品、设备、物模型、消息接入、设备影子、规则和告警。
10. **全链路验收**：跨域联调、多 Pod、并发、故障恢复、安全回归和完整浏览器冒烟。

当前首先为第 1 个子项目编写详细实施计划。完成并验证后依次进入后续子项目，目标在
所有十项通过验收前保持未完成状态。

## 8. 测试与验收

### 8.1 自动化测试

- Java：领域单元测试、权限注解测试、MyBatis 拦截器测试、Testcontainers 数据库与
  Redis 集成测试、MockMvc API 测试、服务契约测试；
- Vue：Vitest 组件和 Store 测试、路由与权限测试、API 契约测试；
- 契约：OpenAPI schema 检查和前端类型生成一致性检查；
- 端到端：真实网关、认证、admin、数据库和 Redis 环境下运行 Playwright 冒烟；
- 性能：登录、权限加载、用户分页和批量授权的基准及并发测试；
- 安全：跨租户越权、水平越权、CSRF、XSS、SQL 注入、SSRF、文件上传、开放重定向、
  令牌重放、内部请求伪造、任意消息目标注入、跨租户消息重放和超限批量重试回归测试。

新增行为严格使用测试驱动：先提交或记录失败测试证据，再写最小实现，通过后重构。
每个功能提交前运行最窄的相关测试；每个子项目结束时运行受影响仓库的完整测试和构建。

### 8.2 多 Pod 验收

至少启动两个目标服务实例，验证：

- 任一 Pod 登录后可访问其他 Pod；
- 权限、租户和组织变更能在所有 Pod 及时生效；
- 并发创建和分配不会产生重复关系；
- 滚动停止 Pod 不丢失已接受的审计事件或异步任务；
- XXL-Job 故障转移后任务不重复产生业务结果；
- MQ 调度 Handler 故障转移后不会重复产生业务结果，未完成批次可从检查点恢复；
- 人工重试、死信重放和延迟消息取消在所有 Pod 上保持一致状态；
- RabbitMQ 补偿可以恢复暂时失败的跨服务事件；
- readiness 能在依赖不可用时摘除实例，恢复后重新接流量。

### 8.3 完成定义

单个功能只有同时满足以下条件才算完成：

1. 数据库迁移、后端 API、权限点和前端页面齐全；
2. 单元、集成、契约和相关浏览器测试通过；
3. 文档、配置示例和安全边界同步更新；
4. 没有真实密钥、默认生产口令、空实现或仅展示的占位页面；
5. 形成一个不含其他任务改动的 Conventional Commit。

整体目标只有在全部十个子项目通过自动化测试、前后端联通、多 Pod 验收和完整冒烟后
才算完成。

## 9. 提交与工作区保护

根工作区、`java-base-module` 和 `node-base-module` 是独立 Git 上下文。每次提交前分别
检查状态和 diff，只暂存明确属于当前功能的文件，禁止使用未经审查的 `git add .`。

当前已存在的根仓库文档改动、`deepseek-harness` 未跟踪目录，以及 Java 文件服务相关
改动都不属于本目标，必须保留在工作区且不能进入本项目提交。后端和前端可以在不同
仓库分别提交；需要联动的功能以同一功能名和对应测试证据关联，而不是强行合并提交。
