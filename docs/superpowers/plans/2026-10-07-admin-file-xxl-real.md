# G2 文件真实 XXL 调度与超额恢复实施计划

**Goal:** 用真实 XXL-Job 3.2.0 管理端、两个 file JVM 和真实 MySQL/MinIO 验证超额分片删除失败的调度恢复、失败回调、自动重试及跨实例路由。

**Architecture:** 建立本轮专用调度数据库/容器及执行器组，禁止临时执行器注册到共享 file-service 组。业务数据使用全新双租户夹具和精确文件目录；复用当前已验证的 admin/file 制品，不修改前端布局。

**Tech Stack:** Python 3 验收器、JDK 21、XXL-Job 3.2.0、MySQL 8、MinIO、现有文件 HTTP 与只读 SQL/S3 探针。

## 边界与证据

- 非空任务参数固定为本轮 `tenantId`、`moduleCode`，不调用空参数全局恢复。
- 验收直接调用管理端创建/触发任务，必须观测同一 jobId 的真实 `triggerCode` 和 `handleCode`；日志存在或 `/run` 接受不等于业务成功。
- 故障代理仅允许本轮物理前缀。真实完成超额对象后阻断 DELETE；失败时记录对象仍在、预留仍在、没有已发布文件/历史用量。
- 自动重试必须由调度端生成新 logId，原失败日志不改成成功。恢复后核对对象/MPU/预留均零、历史上传用量零、原签发终态不可重新发布。
- 双执行器必须有独立实际 PID、相同 JAR 哈希和不同端口，使用 manager 登记地址验证路由。后续故障转移只终止本轮自有进程。
- 周期调度与长期墓碑、媒体任务、后台浏览器完整管理、生产 Kubernetes 仍需各自证据，不能由本次局部通过推导完成。
- 不提交凭据、令牌、签名 URL、uploadId、Cookie、原始 SQL/SDK 错误。报告使用固定分类及白名单字段。
