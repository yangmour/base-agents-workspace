# 管理平台复刻目标与分阶段验收计划

> 执行方式：按独立功能使用 `subagent-driven-development` 或 `executing-plans` 拆解实施、验证并提交。本文件是目标与验收总表；各业务域实施前再编写对应的接口、数据模型和代码任务计划。

**Goal:** 在 `java-base-module/server/admin` 与 `node-base-module/base-admin-web` 上，保留现有前端风格，复用并优化公共模块，逐步交付后台独立认证、系统管理、基础设施及工作流、CRM、ERP、商城、支付、AI、IoT，并通过真实前后端、多租户、多 Pod 和性能验收。

**Architecture:** 管理员身份、凭证、令牌、会话和授权由 `admin` 独立负责；`auth-center` 只负责业务客户端统一认证及 SSO。公共权限、安全、缓存、消息和文件能力优先复用，扩展业务按领域分模块；业务定时调度统一使用 XXL-Job。

**Tech Stack:** 以本仓库 POM、`package.json` 和锁文件为准。盘点时后端为 JDK 21、Spring Boot 3.2.12、Spring Cloud 2023.0.0、MyBatis-Plus 3.5.15、XXL-Job 3.2.0；前端为 Vue 3、TypeScript、Vite 5、Pinia 2、Element Plus。不跟随参考项目批量切换依赖版本。

**盘点日期：** 2026-10-03，Asia/Shanghai。

## 1. 目标边界与执行约束

- 后端正式目标：`java-base-module/server/admin`；前端正式目标：`node-base-module/base-admin-web`。
- `weixin-bot-admin` 的历史实现和测试不能作为正式前端验收结果；不因本任务删除整个相邻项目。
- 参考 [ruoyi-vue-pro / master-jdk17](https://github.com/YunaiV/ruoyi-vue-pro/tree/master-jdk17) 的功能、领域划分与权限体验，参考 [yudao-ui-admin-vue3](https://github.com/yudaocode/yudao-ui-admin-vue3) 的管理功能。两者用于对照需求；本项目代码结构、接口和依赖版本继续以本仓库为准。
- 前端以用户当前已修改的布局、主题、侧栏、表格和弹窗为视觉基线。延续已有风格，新增页面使用同一套样式；不另起一套 new-api 或芋道主题。
- 直接重构，不保留被替代的旧接口、旧认证链、重复配置和无效页面。删除前核对引用及运行入口，避免把仍被其他服务使用的配置当作旧配置删除。
- 复用 `com.xiwen`、`RI<T>`、统一错误语义和已有权限契约。公共能力按实际复用点抽取，不复制第二套权限框架。
- 类、公共方法、实体/DTO 字段、接口参数、权限语义、事务及并发边界补充中文注释；同时描述单位、可空性、状态值及敏感字段用途。
- 每一部分交付都包含可见页面或可调用接口、相关测试、真实联调、文档及独立提交。发现阻断该部分的问题时，同步排查依赖的基础模块并修复。
- 不以空页面、静态示例数据、Mock 测试、编译成功或历史截图代替功能完成。
- 本文件最初交付目标文档和现状核对，随后按真实运行证据更新。下文勾选项只代表对应范围通过，未勾选项仍是后续验收任务。

## 5. 每部分功能的完成标准与提交规则

每个独立功能按下列顺序收口：

1. 明确该功能的页面、API、权限码、租户/数据范围和业务状态变化。
2. 复用现有实现，补齐实际缺口；缺陷先建立可重现证据和针对性回归。
3. 运行受影响后端模块测试、前端测试、类型检查和构建。
4. 在真实前后端及所需中间件上执行正常流程和越权/失败流程；修复后重跑失败用例及受影响回归，直到约定的验收用例全部通过。
5. 记录测试命令、日期、代码版本、测试数据范围、截图/报告位置及尚未执行项；有跳过项不得标为全部通过。
6. 提交该功能相关文件，随后更新进度表中的状态与提交哈希。

状态采用“未开始→实现中→可演示→联调通过→多租户/多 Pod 验收通过”。只有满足该功能全部适用退出条件，才勾选完成。

提交分别落在实际 Git 仓库：

- 根仓库 `case`：跨项目目标、设计与联调文档。
- `java-base-module`：后端及公共模块；例如 `feat(admin): 完善用户数据权限闭环`。
- `node-base-module`：正式前端，路径限定 `base-admin-web/`；例如 `fix(admin-web): 修复权限刷新后的按钮状态`。
- 一个跨仓库功能可形成相互关联的前后端提交，在进度文档中记录完整提交组；不跨仓库假设一个原子 Git 提交。
- 保留用户已有未提交/已暂存改动；不使用全量暂存夹带其他项目、缓存、日志或凭据。配置删除与相关调用清理一并提交。

## 6. 整体完成定义与下一步

整体目标完成要求 G0–G11 的全部适用项通过，参考功能差距表没有未处理的范围内缺口，完整浏览器冒烟和关键业务链可重复运行，双租户隔离、多 Pod 一致性及性能报告具备实际证据。无法以有限测试保证永远没有缺陷；“直到没问题”在交付中具体定义为约定用例全部通过、无已知阻断性缺陷、遗留项明确记录且不能伪装为完成。

**G0、G1 组织/角色、菜单/套餐范围/审计、账户启停与密码重置已完成各自真实复验；下一步补齐 G1 错误密码限流、认证域令牌互换、导出、租户目标规则和异步审计故障矩阵。** 继续按 G1→G2→G3→G4 推进已有模块收口；进入扩展业务阶段后按 G5→G11 交付，避免同时铺开七个只有页面骨架的业务域。
